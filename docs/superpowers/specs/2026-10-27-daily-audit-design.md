## 背景

2026-10-26 至 10-27 连续两天出现「线上数据不更新 / 数据静默缺失」，暴露了当前
产出链的结构性弱点：

| 时间 | 现象 | 根因 |
|---|---|---|
| 10-26 22:27 | 站点被清空成只剩 `.nojekyll` | `open_db` 在库不存在时静默新建空库 → 导出"成功"但无数据 → 部署步骤带 `always()` → peaceiris force-push 推了空目录 |
| 10-27 全天 | 3 个 cron（07:30/07:45/08:30 UTC）一次都没触发 | GitHub schedule 队列对该仓库不可靠（10-26 的 07:30 那班延迟 7 小时至 14:27 UTC） |
| 10-27 | 本地兜底链路也失效 | `a-finder.sh` 用 `uv run`，uv 需写 `~/.cache/uv`，受限环境报错 → 流水线第 2 步中断 |
| 10-26 | 整天数据缺失（选股/计划层） | 行情补抓了但没重跑选股；缺口判定以"库的最后一天"为准，10-26 在基准里不可见 |

已完成的补救（本文档不重复展开，详见 CLAUDE.md）：
退役 Worker 行情层、部署前产物校验（`scripts/verify_site_export.py`）、cron 加密到 8 班、
`a-finder.sh` 改用 venv 解释器、`pick_history --date` 支持补历史、转债错标防护。

## 目标与成功标准

**目标**：确保数据准时、准确、稳定产出。

**时效要求放宽**：原为 15:30 收盘后立即产出，现放宽为**当日 21:00 前产出**。
这从"抢几分钟窗口"变成"有 6 小时可调度窗口"，是本设计成立的前提。

**成功标准**（可验证）：

1. 每个交易日的选股/计划数据，在**当晚 21:00 前**必定出现在线上（`data/dates.json` 含当日）
2. 任意交易日的三层数据（行情/选股/计划）缺失，都能在**当晚巡检中发现**
3. 可自动修复的缺口（选股/计划层、7 天内的行情层）在巡检中**自动补齐**
4. 不可自动修复的缺口，产生**明确告警**，指明缺哪层、哪些日期、为何修不了
5. 巡检无异常时也发**每日心跳**——沉默本身即是故障信号

"当天"在本文档中一律指**巡检运行日的那个交易日**（巡检在 21:00 运行，
当日 15:00 已收盘）。若巡检在非交易日运行（周末/节假日），则：
- 应有交易日集合自然不含当天 → 不会误报
- 仍会检查最近 30 天内是否有历史缺口
- 心跳消息标注"非交易日，仅巡检历史"

**非目标**（明确排除）：

- 不追求分钟级实时性
- 不自动补 7 天以上的行情缺口（理由见「修复策略 → 为什么 7 天是界」）
- 不自动补转债历史（数据源只有实时快照，见「修复策略」的修复矩阵）
- 不改变选股/计划的**计算口径**（本次只改「何时产出、产出后如何保障」）
- ⚠️ 但**确实会改写已发布的组合状态**：L3 的重放以 `paper_trade=True` 执行，
  会写 `open_positions` / `trade_events`，而巡检随后会把库 export+deploy 到
  gh-pages —— 用户在组合页看到的数字会在夜里自己变。详见「已知副作用」。

## 架构

```
 ┌──────────────────────────────────────────────┐
 │ 07:30–09:00 UTC  deploy-site.yml（发布）      │
 │ 8 个密集 cron → 同步 → 选股 → 计划 → 导出     │
 │ → 产物校验 → 部署 gh-pages                    │
 │ 产出：线上当天数据                             │
 └──────────────────────────────────────────────┘
                      │ 写入 hs300.db（Actions cache）
                      ▼
 ┌──────────────────────────────────────────────┐
 │ 13:00 UTC（北京 21:00）daily-audit.yml（巡检） │
 │ 三层体检 → 自动修复 → 复检 → 报告              │
 │ 产出：通知；不改线上当天数据                   │
 └──────────────────────────────────────────────┘

 独立兜底（与上面两条互不依赖）
 ├── Cloudflare Worker cron 07:35 / 08:35 UTC → workflow_dispatch
 │     （依赖仓库 secret GITHUB_DISPATCH_TOKEN）
 └── 本机 launchd 17:10 → a-finder.sh fallback
```

### 职责边界（硬边界）

| 职责 | 归属 | 不属于 |
|---|---|---|
| **产出**（当天数据发布到线上） | `deploy-site.yml` | 巡检不主动发布当天的**选股/计划**（但会重放并覆盖，见「已知副作用」） |
| **体检**（判断哪些日期/哪层数据缺失） | `scripts/audit_coverage.py`（纯判定，无写副作用） | 不发通知、不改数据 |
| **修复**（补历史缺口的选股/计划/行情） | `scripts/repair_gaps.py` | 不补 7 天以上的行情；不补转债 |
| **报告**（通知 / Step Summary） | `daily-audit.yml` + `scripts/notify_audit.py` | — |

**为什么体检与修复拆成两个脚本**：体检是纯读取 + 判定，可写单元测试（构造有缺口的库，
断言能找出）；修复有副作用（写库、跑计算），只在 workflow 中执行。`repair_gaps.py`
消费 `audit_coverage.py` 的输出，不自行重新判定，避免两处口径漂移。

### 为什么巡检要独立 workflow

- 职责单一：巡检失败不影响早班发布
- 巡检逻辑全在 Python 脚本中，**可本地测试、可手动运行**，不等 CI
- 复用与 `deploy-site.yml` 相同的缓存恢复与依赖安装步骤

## 交易日历基准

### 共享模块

新增顶层模块 `market_calendar.py`：

```python
def trading_days(start: dt.date, end: dt.date, *,
                 include_known_weekend: bool = False,
                 known: set | None = None) -> list[str]:
    """[start, end] 内真正的 A 股交易日（ISO 字符串）。

    chinese_calendar 的 is_workday 为 True 但属于周末（调休补班）时，
    A 股不开市：
      - include_known_weekend=False → 一律排除（巡检用：客观基准）
      - include_known_weekend=True  → 该日在 known 里则保留（同步用：库里有就认）
    chinese_calendar 不可用时返回 []（调用方自行降级，绝不猜）。
    """
```

### 两处调用

| 调用方 | 参数 | 理由 |
|---|---|---|
| `sync_service` 缺口判定 | `include_known_weekend=True, known=库内已有日期` | 保持现有行为不变（库里有调休日数据就认） |
| `scripts/audit_coverage.py` 体检 | 默认（`False`） | 客观基准，避免残留数据掩盖缺口 |

### 为什么要抽模块而不是复用 `sync_service._trading_days_from_calendar`

1. 该函数是私有函数（下划线前缀），跨模块调用是坏味道
2. 语义需要分歧：同步要"库里有就认"，巡检要"客观基准"。塞进一个函数会互相污染
3. **口径漂移的代价已经付过一次**：10-26 漏检的根因正是"日历口径散落、各自为政"

### 降级策略

`chinese_calendar` 不可用时返回 `[]`（而非 `None`）：

- 巡检：拿到空列表 → **跳过体检并报警**（"日历不可用，无法判定基准"），绝不猜
- 同步：`if not expected_from_calendar` 走既有的"市场日历 + 尾部窗口"回退分支，行为等价

## 三层缺口判定

### 应有交易日集合

```
应有日 = chinese_calendar 工作日 ∩ [今天 - 30 天, 今天]
```

用 30 天窗口（覆盖一个长假 + 足够冗余）。**基准完全独立于库内数据** —— 这与现有
`scripts/check_gaps.py`（以库内数据推导基准）的根本差异，正是 10-26 漏检的成因。

### 判定矩阵

| 层 | 数据表 | 判定条件 | 修复方式 |
|---|---|---|---|
| **L1 行情** | `daily_prices` | 该日 `COUNT(DISTINCT code) < 280` → 缺 | 近 7 天自动补抓；更早只报警 |

**阈值 280 的由来**：沪深300 成分股 300 只，历史上单日实际覆盖约 299 只（个别成分股
停牌，如 601059 信达证券自 2026-09-14 起停牌）。280 留出约 6% 的停牌/新纳入缓冲。
阈值取固定值而非动态比例，是为了让判定可预期、可手工复核。
| **L2 选股** | `daily_picks` | 该日**无行** → 缺 | 自动补算（纯计算） |
| **L3 计划** | `trade_plan` | 该日**任一档位无行** → 缺 | 自动补算（纯计算） |

**L2/L3 只在"完全没行"时才算缺**，不用行数阈值 —— 选股数量天然波动（10-27 为 77 条，
10-26 为 55 条，10-23 为 67 条），行数阈值会产生大量误报。

### L3 的档位齐全

```
期望档位 = {5W, 10W, 15W, 20W, 25W, 30W, 35W, 40W, 45W, 50W, default}
判定：该日实际 portfolio 集合 ⊉ 期望档位 → 缺
```

补的时候一次性补全 10 档 + default，不按需补单个档位 —— 避免"补了一半，下次巡检
仍判定为缺"的碎片化。

### 层级关系

```
L1 缺 → 只报 L1，不报 L2/L3（没有行情算不出选股，报了是噪声）
       → 修复 L1 后重新判定，再看 L2
L1 齐、L2 缺 → 报 L2
L1 齐、L2 齐、L3 缺 → 报 L3
```

报告需能直接看出**根因**：例如"10-26 缺 L2/L3，根因是 L1 行情在 10-26 为 0 只"，
而非平铺三层缺失让人自己推断。

## 修复策略

### 修复矩阵

| 缺口 | 自动修复 | 方式 | 失败后 |
|---|---|---|---|
| L1 行情（7 天内） | 是 | `sync-hs300-range --gap-fill` | 转报警 |
| L1 行情（> 7 天） | 否 | — | 报警 |
| L2 选股 | 是 | `pick_history --date D --no-sync` **+ 当天的 L3 命令**（见下） | 转报警 |
| L3 计划 | 是 | `plan build --date D`（每个缺失日期）+ `plan build-all --backfill --since <最早缺口日>` | 转报警 |
| L1 缺导致的 L2/L3 缺 | 先修 L1，再修 L2/L3 | 补行情 → 补选股 → 补计划 | 任一步失败即停，余项转报警 |
| 转债 | 永不自动 | 数据源仅实时快照 | 不报（已知限制） |

**L2 缺口必然连带 L3**：选股没有 → 当天计划也无从生成（`audit_coverage` 见 L2 缺
就 `continue`，不会再报 L3）。只补选股的话，选股一落地计划立刻成为缺口，复检仍
rc=1，得跑第二轮才收敛。所以 L2 的修复动作里同时带 `plan build --date D` 与一次
`plan build-all --backfill`（`--since` 取 L2∪L3 并集的最早日；命令不重复生成）。

**L3 的命令形态**（最终实现）：

```
plan build --date D            # 每个缺失日期一条，补 portfolio="default" 档
plan build-all --backfill --since <最早缺口日>   # 全档位重放，只有一条
```

`plan build` 写 `default` 档，`build-all` 写 5W..50W 十个档位 —— 体检期望的
档位集合含 `default`，缺一不可。

### 补计划的真实语义：重放，不是「只补缺失日期」

⚠️ 早期设计写的是「只补缺失日期，绝不重算已有日期」。**实现不是这样**：

`plan build-all --backfill --since <最早缺口日>` 会按缺口日**往后重放**所有日期：

- **完整日期**（该日各档位都齐全）命中原 `params_hash`，走 `build_plan` 的缓存短路
  → 结果不变；
- **部分缺失**的日期会用**当前** `open_positions` 重建 → 补出的历史计划反映的是
  **重建时**的持仓状态，不是当时的快照。

实测（2026-10-26 缺口，2026-10-28 复现）：重放后该日 `trade_plan` 行数与原始不相等。
要原样快照只能靠备份，不能靠重放。

之所以从「最早缺口日」重放而不是只补那几天：paper-trade 的持仓/资金曲线需要从
缺口日起按库内已有状态往后推进 —— 缺口日之前的 carryover 不重放。

### 为什么 7 天是界

- **7 天内**：数据源仍提供该日行情，自动补抓代价小（一次区间请求），成功率接近 100%
- **超过 7 天**：需抓更长历史区间（可能数百天），耗时长、限流风险高、CI 分钟贵；
  且历史行情的复权口径可能已变化（数据源的 `fqt` 行为会调整），补出的数与当初不同
  → 污染历史序列
- 原则：**宁可报警让人处理，也不要用口径不一致的数据填历史**

### 修复后复检

```
repair_gaps.py 修复 → audit_coverage.py 重跑 → 三层全绿 = 成功
                                        → 仍有缺口 = 该项转报警（不重复修）
```

复检步骤是必需的：否则会重演"补了行情但选股没补上却以为修好了"（10-26 的成因）。

### 幂等性

`pick_history --date D` 与 `plan build --date D` 均按日期 upsert，重复执行不产生重复行。
但 CLAUDE.md 记录过「回补会用不同 `params_hash` 追加重复行」，因此巡检补 10 个档位时
必须验证幂等 —— 实现时需对同一日期连续跑两次 `build-all --date D`，比对行数不变。

**实测结论（2026-10-28）**：同一日期连续跑两次 `build-all`，`trade_plan` 行数不变
（`params_hash` 相同 → `ON CONFLICT` 更新而非追加）。但**幂等只保证「不追加重复行」，
不保证「内容与当初一模一样」**：重放会改写组合状态（见「已知副作用」）。

### 修复后的发布

补好的历史日期**要发布到线上**（否则「库里补了但页面看不到」）。做法：

1. 重新导出（`export_json.py`）→ `scripts/verify_site_export.py` 校验 → 部署 gh-pages
2. 复用产物校验守卫（10-26 站点被清空的那类操作）

⚠️ 「不重算当天」这条早期设计没有兑现：`build-all --backfill --since` 会一路重放到
今天，当天已有的计划也可能被覆盖。见「已知副作用」。

### 已知副作用（重要，读之前先想清楚）

**1. 组合状态漂移（用户可见）**

L3 的重放以 `paper_trade=True` 执行，会写 `open_positions` / `trade_events`；
巡检随后把库 export+deploy 到 gh-pages，所以**用户在组合页看到的数字会在夜里自己变**。

实测（2026-10-28，/tmp 副本上端到端复现，补 10-26）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `open_positions` 行数 | 535 | 542（+7） |
| `trade_events` 行数 | 1048 | 1055（+7） |
| 10W `holdings.count` | 7 | 8 |
| 10W `size_total` | 0.8313 | 0.95 |
| 10W `cash_remaining` | −2285 | −12315 |

5W / 15W~30W 与 summary 同样变化。

**2. 这条副作用必须显式化，不能只写在文档里**

- `scripts/repair_gaps.py`：修复前后各数一次行数，写进 `--out` 的 `side_effects` 字段
  （`{"open_positions": {"before": 535, "after": 542, "delta": 7}, ...}`）；
- `scripts/notify_audit.py`：读到 `side_effects` 有变化就在通知正文加一行
  「副作用：修复重放改写了组合状态（open_positions +7、trade_events +7）
  —— 组合页数字可能与修复前不同」。

不记录 = 没人知道数字为什么变了，用户只会以为系统出 bug。

**3. 幂等性实测结论**

见上一节：重复跑不会追加重复行，但会改写组合状态。**「幂等」不等于「无副作用」。**

## 报告与通知

### 三种结局

| 结局 | 判定 | 通知内容 |
|---|---|---|
| ✅ 通过 | 无缺口 | 每日心跳：`✅ 10-27 巡检通过｜近 30 天三层无缺口`（**不**宣称「当天数据已发布」—— 这条路径不导出/部署，无从核实） |
| 🛠 已自动修复 | 检出缺口 → 修复成功 → 复检通过 | 缺了什么、怎么修的、复检结果；有副作用时附一行说明 |
| 🚨 需人工 | 检出但修不了（> 7 天 / 补抓失败 / 复检仍缺） | 缺哪层、哪些日期、为何修不了、建议做法 |

**心跳是必要的**：静默失败最难排查。10-26 的站点清空与 10-27 的 cron 未触发，
都是靠人发现的。有了心跳，"今天没收到消息"本身就是信号。

**非交易日的标注**：非交易日跑巡检只有「巡检历史」，没有当日新增产出。标注必须
**同时**进 Step Summary 和 ntfy 推送正文（`--non-trading-day`）—— 只写 Step Summary
的话，手机上收到的推送仍会被读成「今天的数据已更新」。

### 通知通道（分级降级）

1. ntfy（若配了 `NTFY_TOPIC`）→ 手机推送
2. GitHub Step Summary（总是写）→ Actions 页面可查
3. 仓库 issue（可选）→ 留痕，不依赖通知渠道

至少 1+2 永远生效：即使未配 ntfy，巡检结果也在 Actions 页面留痕。

### 失败处理原则

| 场景 | 行为 |
|---|---|
| 日历不可用 | 跳过体检 + 报警，绝不猜基准 |
| 体检脚本报错 | run 变红 + 报警，不静默跳过 |
| **体检报告没落盘** | **run 变红 + 报警**（rc=2 + 🚨），绝不当作「没有缺口」 |
| **显式传了原报告却读不到** | **run 变红 + 报警**（rc=2 + 🚨），绝不降级成「没有对照」 |
| 某项修复失败 | 记为"需人工"，继续修下一项，不中断整体；**run 变红** |
| 复检仍缺 | 转"需人工"，不重复修（避免无限循环） |
| 发布补好的历史数据失败 | 线上保持旧版本（不破坏），报警 |

"不中断整体"是关键：巡检要尽可能多修几项，一项失败不该挡住其它项。

### 「报告没落盘」为什么是最危险的一种失败（2026-10-28 评审复现）

失败链条：体检有缺口 → 写盘失败 → 报告不存在 → 修复步拿不到报告（rc=2）→
复检干净（rc=0）→ 通知步读到「不存在的原报告」→ **静默降级成「没有对照」** →
`discovered=[]`、`fixed=[]` → 打印「✅ 巡检通过」，run 还是绿的。

评审复现的输出就是一条绿色心跳，唯一线索是一条 warning。这条链路存在的意义
就是消灭这种失败形态，所以三层都要堵：

1. `audit_coverage.py`：写盘失败 → rc=2（与「无法判定」同级），且**先写盘再打印**，
   报告没写出来就不许先打印「✅ 三层无缺口」；
2. `daily-audit.yml`：体检步检查 `/tmp/audit.json`、复检步检查 `/tmp/audit2.json`
   是否落盘（`[ ! -s ... ]`），没有就 `::error::` + exit 1；
3. `notify_audit.py`：显式传了 `--audit-pre` 却读不到 → 致命错误（rc=2 + 🚨）。
